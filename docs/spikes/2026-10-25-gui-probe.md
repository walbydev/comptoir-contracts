# 2026-10-25 — Can our frame replace a container's GUI?

**Question.** When the counter (a `container`) is opened, does `player.opened = nil` inside
`on_gui_opened`, followed by a frame added to `player.gui.screen`, **replace** the vanilla inventory
frame — or do the two stack?

**Why it could not be answered here.** A spike measured that `game.create_player` does not exist in
2.1.23, that `game.gui` does not exist, and that a `LuaPlayer` only appears when a client connects.
Headless therefore has no player, no `player.gui`, and `on_gui_opened` receives zero events. The
whole GUI layer is untestable without a screen (ADR `0050`).

**Instrument.** `spike/gui-probe/comptoir-gui-probe_0.0.1` — thirty lines: on open, clear
`player.opened`, add a frame with two labels and a `close` button, print the entity name.

**Result, on the requester's graphical client, 2026-10-25.** The probe frame appeared; **no vanilla
inventory grid behind it**.

**Conclusion.** The replacement works. The counter keeps its `container` prototype, `0045`'s option B
(an energy-capable machine) stays rejected, and the window can be written on a foundation that has
been seen working.

**How this was proven, and what it does not prove.** One visual run, one pair of eyes, no automated
check. A regression in which the vanilla frame reappears would be caught only on the next build, by
the same eyes — which is why the by-eye rows of `docs/09-tests.md` exist and why `make accept` refuses
to report green until they are recorded.

**Side finding, kept because it costs an afternoon to rediscover.** `--start-server` does not tick
without `"auto_pause": false` in the server settings. The server sits at tick 0, no script runs, and
the mod looks broken.
